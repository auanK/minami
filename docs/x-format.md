# X Format

Status: normative contract 1.0. M0 inspection, extraction of `control.json` and `source.json`, its independent coverage audit, structural validation, lexical XHTML reconstruction, and M2.2 EPUB packaging/verification/publication through `minami build` are implemented. Build accepts one or more complete X response envelopes, reuses the authenticated snapshot for every resource, and publishes without replacing an existing destination. No normative rule or schema of X 1.0 changes in M2.2.

## Purpose and scope

X separates translation content from the information needed to put it back into an EPUB. Minami identifies and maps content; an external translator supplies text. The translator never supplies authoritative XHTML, attributes, resource paths, or reconstruction instructions.

The serialization is JSON. Extraction uses the existing EPUB 2 ZIP, package, spine, and NCX readers; it adds no parallel EPUB reader and does not change `InspectionReport` or the existing inspection API. The complete XHTML vocabulary is listed below. ZIP metadata policy and implementation budgets are documented in [architecture](architecture.md) and [development](development.md).

The words **must**, **must not**, and **reject** below define the unchanged contract for extraction, coverage auditing, structural translation validation, reconstruction, and the builder. References below to future implementation preserve the original specification's historical wording.

## Files and authority

```text
work/
├── control.json       # Minami's reconstruction map; never translation input
├── source.json        # generated translation input
└── translated.json    # external translation response
```

These are data files, not a new container format. The original EPUB is supplied separately by the operator; its filesystem location is not embedded in translation input. Filenames are conventions, not identities. Multiple response files may represent independent batches.

Every X file must be one strict JSON object encoded in UTF-8 without a BOM. Duplicate object keys at any nesting level, trailing non-whitespace data, missing fields, unknown fields, and wrong field types are rejected. No comments or JSON repair conventions are defined.

| Artifact | Contents | Authority |
| --- | --- | --- |
| Original EPUB | Original bytes, tags, attributes, and resources | Source of truth, explicitly selected by the operator |
| `control.json` | Version, origin digest, document/section/segment mappings, protected token locations | Must match a map regenerated by Minami from that original |
| `source.json` | Segment IDs and source parts | Derived convenience input, never a reconstruction authority |
| `translated.json` | Segment IDs and target parts | Untrusted text plus claims about protected token placement |

Keeping `control.json` out of the translator's write area is useful but is not the integrity mechanism. Validation and build regenerate the map from the selected original, compare all fields, and use only the regenerated map. A checksum stored beside editable metadata cannot authenticate that metadata. No signatures, secrets, or trusted storage service are required by this contract.

## Version, identity, and determinism

All artifacts have `format_version: "1.0"`, which identifies the current intermediate format. Extraction, validation, and build use one XHTML vocabulary. Unknown elements are rejected. `control.json` has no XHTML selector; validation and build regenerate extraction from the original EPUB and require an exact control match. A format schema change requires a format version change.

`source.epub_sha256` is the lowercase, 64-hex-character SHA-256 digest of the **complete original ZIP bytes**, not a filename, OPF identifier, or concatenation of resources. Repacking the source ZIP changes its identity even if its XHTML is unchanged.

`extraction_id` is the lowercase SHA-256 digest of this exact UTF-8 sequence, including the final LF and with no BOM:

```text
minami-x\n1.0\n<source.epub_sha256>\n
```

Here `\n` denotes one byte `0A`; `<source.epub_sha256>` is replaced by the 64-character digest, without brackets. This framing contains no timestamps, locale, absolute paths, or random values.

| Identity | Scope and generation |
| --- | --- |
| `d1`, `d2`, … | Documents, once each, in the order defined below |
| `q1`, `q2`, … | Sections, globally numbered by document order then source position |
| `s1`, `s2`, … | Segments, globally numbered by document order then source position |
| `i1`, `a2`, `br3`, … | Markers, local to a segment; role plus one shared counter in source traversal order |

Counters start at 1, use decimal digits without leading zeroes, and are not reset by sections or batches. Marker counters alone reset for each segment. Their role is the original supported element's local name, or `nbsp`, `space`, `comment`, or `pi` for the special atoms below. A marker's role is a readable hint, not authority to create a tag.

A permanent segment identity is `(extraction_id, segment_id)`. It does not depend on translated text, section titles, batch size, or processing order. Stability is promised for the same source bytes, not across edited editions or repackaged EPUBs.

Minami emits arrays in their defined source order and object fields in the order listed in this specification, using UTF-8, two-space indentation, LF, and one final newline. Ordinary Unicode is emitted directly; JSON-required escaping is applied. Input object key order is irrelevant. Translation record order is also irrelevant to association; part order is meaningful.

## Physical documents, navigation, and sections

### Document coverage

Each manifest XHTML resource is represented exactly once. Unique spine documents come first, in spine order, including `linear="no"`; remaining manifest XHTML documents follow manifest order. Repeated spine references retain their original positions but do not duplicate a document or its segments. Order for a non-spine document is an extraction order, not an invented reading order. This includes NCX-only destinations and manifest footnote documents without crawling links.

Other ZIP resources remain untouched. Unmanifested XHTML is outside extraction coverage; successful coverage means all declared manifest XHTML, not every potentially readable object in the ZIP. Missing or unsupported required resources still fail through the existing EPUB infrastructure.

`control.spine` reuses the M0 `idref`/`linear` representation. `control.navigation` reuses M0 navigation fields, order, and zero-based depth/position. Paths resolve through the existing normalized EPUB path rules. Navigation titles remain source metadata; they are not identifiers or translation fields.

### Section boundaries

A section is a non-overlapping source interval used to assign content once. The NCX tree is retained separately in `navigation`; a parent navigation entry may select its section plus its descendants' sections for translation. The parent's own interval does not duplicate its children's text.

For each document:

1. Establish the raw byte interval inside its single XHTML `body`.
2. Map an NCX destination without a fragment to the beginning of that interval. It is not an invented fragment and does not automatically mean the whole document if later destinations exist.
3. Resolve a nonempty fragment against exactly one unqualified `id` on an XHTML element. Such IDs must be nonempty and unique throughout each XHTML document. A missing target, an empty fragment, a target outside the body, or reliance on `name`/`xml:id` fallback is rejected. This is stronger than M0 inspection, which does not resolve fragments.
4. A target block/container starts a section immediately before its opening tag (a target on `body` uses the body interior start). An inline target can move the boundary to the beginning of its enclosing flow group only if everything before it in that group is ordinary XML whitespace or opening tokens of its ancestors. A target after linguistic text or a protected atom would split a segment and is rejected; no phrase is silently split to accommodate it. An opaque descendant, such as an ID inside SVG or a callout atom, cannot establish a section boundary.
5. Sort distinct normalized boundaries by physical source position, add body start/end, and form consecutive half-open intervals. Equal boundaries are aliases of one section; retain every matching navigation position. Navigation order and hierarchy are never rewritten to match this sort.
6. A prefix before the first NCX target, or a whole document without NCX targets, has a section with `navigation_positions: []`. No chapter association is guessed across documents. Sections with no translatable content remain represented. An empty body has one empty section.

Thus navigation entries may share a section, and different sections may share one physical XHTML. Each segment belongs to exactly one section. IDs follow physical order, not titles or the order in which translations arrive. NCX hierarchy is interpreted from `depth` using the existing preorder contract; it does not assert that all associated byte intervals are nested DOM elements.

## Linguistic segments

Extraction works on XHTML body content in source order, not one segment per XML text node or one chapter per file. A paragraph or heading with inline content is one segment, including text before, inside, and after inline elements. A dialogue paragraph is treated as a paragraph; dialogue detection is not added.

The supported vocabulary is explicit:

| Role | Elements and handling |
| --- | --- |
| Flow containers | `body`, `div`, `center`, `blockquote`, `p`, `h1`–`h6`, `li`, `dt`, `dd`, `td`, `th`, `caption` |
| Structural containers | `ol`, `ul`, `dl`, `table`, `thead`, `tbody`, `tfoot`, `tr`, `colgroup`; recurse without joining different children |
| Paired inline elements | `i`, `b`, `em`, `strong`, `span`, `a`, `sup`, `sub`, `big`, `small`, `font`, `del`, `s`, `u`, except the opaque cases below |
| Atomic content | `br`, `img`, a complete SVG subtree, comments, processing instructions, empty inline subtrees, protected spaces, and a complete `sup`/`sub` containing a link |
| Preserved boundaries | `hr`, `col`, opaque `script`/`style` subtrees; none supplies editable text |

Within each flow container, a maximal consecutive group of direct text and inline/atomic children is one unit. A block or structural child ends the group and is traversed independently. This covers text directly in a `center`, a list item, a table cell, or either side of a nested table without extracting parent and child text twice. Paired inline elements may contain only supported inline/atomic content, not blocks.

Paired inline elements use markers to expose their text for translation while retaining original opening and closing tag bytes, attributes, and nesting during reconstruction. Visual styling can vary between EPUB readers.

Structural child relationships are `ol`/`ul` → `li`; `dl` → `dt`/`dd`; `table` → `caption`/`col`/`colgroup`/`thead`/`tbody`/`tfoot`/`tr`; `thead`/`tbody`/`tfoot` → `tr`; `tr` → `td`/`th`; and `colgroup` → `col`. Whitespace, comments, and processing instructions between those children are preserved. Unexpected direct linguistic text or other children are rejected rather than discarded. Unknown elements/namespaces with unclassified content are unsupported, not guessed to be inline or silently skipped.

A group becomes a segment if it contains decoded text other than XML whitespace after opaque atoms are removed. Numeric text also counts. An inline subtree without eligible editable text is atomic as a whole; it has no nested marker records. A whitespace-only or atom-only group remains byte-for-byte untouched and creates no translation task. A segment's replacement interval is that complete group's original lexical span; it excludes its enclosing block tags and cannot cross a section boundary. All segment intervals in a document are disjoint.

Tables retain their original cell/row/nesting structure. Text in `th`, `td`, captions, and nested paragraphs is eligible; no segment crosses cells. Images and SVG are immutable objects, not OCR input. Footnote prose in paragraphs/list items is eligible; a linked superscript/subscript callout is one opaque atom, including its label, `id`, destination, and nested tags. Other `sup`/`sub` text can use paired markers. An ordinary link's visible prose is translated while all its attributes remain original. Links are not fetched; their original destinations, including external ones, are copied verbatim.

All attributes are outside translation, including `href`, `id`, `src`, `class`, `style`, `title`, `alt`, and language attributes. Head content, including document titles, is outside extraction. Text in SVG, scripts, and styles is intentionally not translated. These exclusions are coverage boundaries, not evidence that every visible string in a rendered book has been translated.

## Inline representation: decision

The chosen representation is **C: separate control metadata plus B-style structured parts**. It is one format: parts provide the editable syntax, while the control map supplies immutable token identity and source locations. The alternatives are compared here to make that decision explicit.

| Criterion | A: marker strings | B: parts alone | C: parts plus separate control (chosen) |
| --- | --- | --- | --- |
| LLM readability | Compact prose, fragile delimiters | More JSON, complete sentence remains together | Same parts; only necessary IDs and content reach the translator |
| Rust validation | Requires a second token grammar | Tagged cases and a stack | Same simple grammar, checked against regenerated source facts |
| Structural authority | A string cannot establish it | A returned parts list cannot establish it | Original EPUB establishes it |
| Nesting | Custom delimiter parser | Explicit open/close stack | Stack plus immutable source-parent relationships |
| Reordering | Possible if delimiters survive | Move paired groups | Move paired groups within the original parent/segment, subject to global atom order and ID-anchor placement |
| Literal collisions | Literal sentinel syntax needs escaping | Text and tokens have different JSON types | No sentinel reservation in prose |
| Escaping | JSON plus sentinel escaping | JSON only | JSON only; XML escaping occurs during reconstruction |
| Reconstruction | Still needs a trusted map | Still needs a trusted map | Map is an explicit part of the contract |

A segment in `source.json` or a translation response has exactly `id` and `parts`. Each part has **exactly one** of these fields, whose value is a string:

| Part | Meaning |
| --- | --- |
| `{"text":"words"}` | Editable Unicode text, never markup |
| `{"open":"i1"}` | Original paired inline start token |
| `{"close":"i1"}` | Corresponding original end token |
| `{"atom":"br2"}` | One complete protected source object or special space |

Source generation merges adjacent text parts and omits empty text parts. Responses may split or join adjacent text parts; concatenation has the same meaning. Text-part count is not an invariant. Markers must retain their exact identities, multiplicities, and ancestor relationships. Every source segment and each paired marker's subtree must retain some non-whitespace editable text in its response; this rejects accidental blanking, not untranslated prose. Source inline subtrees without such text are atoms instead of pairs.

The global sequence of atoms and the relative placement of ID-bearing anchors are immutable under the rules below; paired markers without IDs are not globally frozen. Both generated source and returned target `text` parts must exclude U+00A0, U+2007, and U+202F. Eligible original occurrences are represented by existing atoms, never by editable text.

For example, `[[OPEN_1]]` inside a text part is ordinary literal text. A target text part containing `<script>` is also literal text and must be XML-escaped, never interpreted as a tag. There is no `html`, `attributes`, `path`, or arbitrary token-definition field in a response.

## Control schema

All listed fields are required. Arrays may be empty where the source has no corresponding content. No additional fields are accepted in version 1.0.

Atomic-order and ID-anchor checks are derived from the existing marker records and original XHTML spans. No anchor flag, ordering field, or other schema addition is required; X 1.0 uses the same representation throughout.

| Record | Fields |
| --- | --- |
| Control root | `format_version`, `extraction_id`, `source`, `spine`, `documents`, `navigation`, `sections`, `segments`, `preserved` |
| `source` | `epub_sha256`, `epub_version`, `package_path`, `ncx_path`; strings obtained from the original |
| Document | `id`, `manifest_id`, `path`, `body`; `body` is a byte interval |
| Section | `id`, `document_id`, `range`, `navigation_positions` |
| Segment | `id`, `document_id`, `section_id`, `range`, `markers` |
| Paired marker | `id`, `kind: "pair"`, `parent`, `open`, `close` |
| Atomic marker | `id`, `kind: "atom"`, `parent`, `range` |
| Preserved record | `document_id`, `range`, `reason`; reason is `atom`, `svg`, `script`, or `style` |

`spine` and `navigation` use the M0 field shapes described above. `parent` is the nearest enclosing paired marker ID in the same segment, or `null`. A complete atomic subtree has no nested marker records. Markers are listed by source start position; only emitted markers consume their segment's counter. `preserved` records identify atomic source spans and script/style subtrees outside segment ranges, including atoms in groups without editable text. SVG roots use reason `svg`, other atoms use `atom`. An atomic subtree is recorded once, without nested preserved records; anything already represented by a segment marker is not recorded again. Preserved records follow document/source order. Structural tags and ordinary whitespace-only text are implicitly preserved by the extraction rules.

Every interval is `[start, end)`, using zero-based byte offsets into the **original uncompressed XHTML bytes**, including any initial BOM. End is exclusive. Bounds are nonnegative JSON integers no larger than `2^53 - 1`, within the document, and on lexical UTF-8 boundaries; each entity reference is indivisible. Numeric strings and fractional numbers are rejected. Sections partition the body interval; segment intervals lie entirely within their owning section. Marker spans lie inside their segment and match its original XML token tree. Nested markers may nest spans; unrelated spans cannot overlap.

There are no copied XHTML strings, attribute dictionaries, parser node IDs, or XPath expressions in control. Original byte intervals locate opening/closing tags and atomic subtrees. The whole-EPUB digest plus regeneration guards those bytes, so additional per-text or per-slice hashes are not required. The public M0 model remains separate: these are additional private X records, not replacements for inspection types.

## Translation schema and batching

Source and response envelopes have exactly `format_version`, `extraction_id`, and `segments`. An envelope carries a full extraction or any chosen subset. Document paths, byte offsets, section titles, token definitions, and source checksums are deliberately absent. The translator copies envelope identity and segment IDs and edits parts according to the marker rules.

Source for the complete mapping example:

```json
{
  "format_version": "1.0",
  "extraction_id": "53a52d4b44bbde450420c79cc6442d9fb5249c5343ea21265e1f4b7d63535fe5",
  "segments": [
    {"id": "s1", "parts": [{"text": "I said "}, {"open": "i1"}, {"text": "this"}, {"close": "i1"}, {"text": "."}]},
    {"id": "s2", "parts": [{"text": "Next"}]},
    {"id": "s3", "parts": [{"text": "Done."}]}
  ]
}
```

A valid complete response, deliberately returned in a different record order:

```json
{
  "format_version": "1.0",
  "extraction_id": "53a52d4b44bbde450420c79cc6442d9fb5249c5343ea21265e1f4b7d63535fe5",
  "segments": [
    {"id": "s3", "parts": [{"text": "Pronto."}]},
    {"id": "s1", "parts": [{"text": "Eu disse "}, {"open": "i1"}, {"text": "isto"}, {"close": "i1"}, {"text": "."}]},
    {"id": "s2", "parts": [{"text": "Seguinte"}]}
  ]
}
```

The local batch selection is simply an expected set of segment IDs, selected by Minami/the operator from control. It is not taken from a returned response. It may be stored temporarily by the caller but is not a permanent X identity. A section selects its own segments; selecting a navigation subtree takes the union of associated sections without duplicate segments. Smaller batches do not renumber anything.

Each batch response must exactly cover the requested set, regardless of order. A valid batch is only partial work unless it covers the entire extraction. Final validation uses the full control segment set: missing, unexpected, and repeated IDs across all supplied responses are errors. Duplicate results are rejected even if their text matches; no last-writer-wins merge is defined. Choosing between revisions is an explicit operator action before final validation.

Additional context belongs in a separate read-only message or caller-managed context file, not inside the response schema. It can include neighboring prose, marker explanations, or section titles, but is never applied to the EPUB. A response containing prose, a Markdown fence, malformed JSON, duplicate object keys, or extra context fields must fail parsing rather than be repaired or have JSON guessed out of it. No particular model behavior or API is assumed.

## Validation invariants

### Identity and authority

1. The operator-selected original must match the control origin digest. Regenerated control must equal supplied control by field values and ordered arrays, independent of JSON object key order.
2. The response version and `extraction_id` must equal the regenerated extraction. Re-labeling a response cannot prove linguistic provenance: SHA-256 binds the expected source bytes, not the honesty or quality of translated text.
3. Document, section, and segment IDs must be unique in their scopes, and every relationship must resolve. Source arrays and intervals must match regeneration exactly. Every requested segment appears exactly once; final success requires the entire extraction, including non-spine content selected by the current rules.

### Protected structure

4. For each source paired marker, the response has exactly one `open` and one `close` with that ID. Each source atom appears exactly once as `atom`. No unknown IDs, new markers, changed token kinds, or markers borrowed from another segment are accepted.
5. A left-to-right stack must close the most recently opened marker. The nearest enclosing paired marker of every pair and atom must equal its source `parent`. Balanced but reparented markup is invalid. Direct sibling paired groups may change order or move relative to text only when the atomic-order, ID-anchor, and NCX constraints below still hold. Their complete nested groups move together; nothing crosses segments.
6. For each segment, scan its regenerated source parts in order and collect every `atom` ID into sequence `A(source)`, ignoring `text`, `open`, and `close`. Scan the target the same way and require `A(target) = A(source)` exactly. This is global within the segment, regardless of the atoms' parents. Moving a paired group is rejected if it changes this sequence, even when its topology and marker multiplicities remain valid. The rule does not freeze the global order of paired markers; permissible movements must satisfy all invariants together. Atom bytes always come from the original.
7. Original tags, attributes, link/reference values, namespaces, and empty elements are copied from original token spans. Target text is always escaped character data. Structural fields supplied by a translator are rejected, never interpreted or merged.

### XHTML IDs and navigation anchors

An anchor marker is a paired marker whose original XHTML element carries an unqualified `id`, or an atom whose original span contains such an element. This is determined from actual elements in the regenerated original, not from a marker's name or any claim supplied by the translator. Every such ID is protected, whether referenced by NCX, another document, or no known link. IDs on enclosing blocks outside a replacement interval remain untouched automatically.

Define a segment's structural event sequence `E` by keeping only its `open`, `close`, and `atom` parts. Each event is identified by `(part kind, marker ID)`. After exact multiplicity is checked, require the following for every anchor event: the **set of event identities before it** in target `E` must equal the set before it in source `E`. A paired anchor has two checked events, its `open` and `close`; an atomic anchor has one. Comparing sets rather than ordered prefixes allows unanchored pairs on the same side of each anchor to reorder when the other invariants permit. No marker may cross an anchor boundary, whether the anchor or the other group is the one being moved. This also preserves nested anchor placement without freezing all paired siblings.

Text is excluded from `E` and may be translated and reordered around an anchor, subject to the nonblank-content rules. An empty anchor such as `<a id="chapter"></a>` inside a segment is an atom: it retains its marker identity, exact source bytes, attributes, ancestry, global atom order, and anchor-event placement. Having no editable text never permits removal or duplication. Outside segments, its original interval remains preserved without a translation task.

NCX targets use this same ID policy. A marker that establishes a promoted NCX boundary additionally must still precede all linguistic text and other non-ancestor markers in that flow group, except leading XML whitespace and ancestor opening tokens. It cannot move that navigation target into the middle of translated prose. These requirements are cumulative and derived from the original navigation and markers; there is no competing NCX-specific policy for moving IDs. Structural placement does not prove that the anchor still identifies the semantically equivalent words in the translation.

### Text, coverage, and completion

8. JSON strings must decode to Unicode scalar values valid for XML 1.0; reject unpaired surrogates and prohibited XML characters even if a JSON parser accepts them. Additionally, every source and target `text` part must exclude decoded U+00A0, U+2007, and U+202F, including occurrences written as JSON Unicode escapes. Reject rather than normalize, convert, or fabricate atoms. Do not normalize Unicode, case-fold, trim, or collapse text. Neither a text-bearing source segment nor any paired marker's target subtree may become empty or whitespace-only after atoms are excluded. For this check, whitespace is exactly XML whitespace (U+0009/U+000A/U+000D/U+0020); protected-space scalars occur only as atoms, not in `text`. Identical source/target text is structurally valid; the validator cannot prove translation occurred.
9. Extraction coverage must account for every body text character exactly once as editable text, a protected atom, an explicitly preserved span, or unchanged ordinary whitespace. Markup, comments, and processing instructions are structural data, not linguistic text. No eligible text may disappear between nested containers or section boundaries. A document with no linguistic text legitimately has no segments. Attributes and head content are excluded by the extraction rules, not silently missed by traversal.
10. All parsing and reconstruction checks complete before reporting success or replacing an output EPUB. A structurally valid subset is not a complete translation. Future readers must bound JSON bytes, part counts, XHTML nodes, and nesting and reject limit violations without truncation; concrete implementation budgets do not grant permission to weaken these invariants or M0 limits.

Errors must distinguish syntax, origin/version mismatch, control mismatch, coverage failure, unknown/duplicate/missing segment, marker multiplicity/topology/global atom order, ID-anchor placement, protected-space-in-text, and invalid character/part shape. Where known, diagnostics include original document path, section ID, segment ID, marker ID, and response part index. Whole-file syntax/origin failures may have no segment context. These diagnostic categories are implemented by the translation validator; no additional Rust error variants are required.

## XML, entities, whitespace, and Unicode

XHTML requires well-formed XML 1.0, UTF-8 (an optional BOM is preserved), an XHTML `html` root, and one `body`. Minami does not perform DTD validation or repair malformed markup. Legacy `center` and `font` are deliberately included because the reference book uses them despite its XHTML 1.1 declaration.

A DOCTYPE may be absent or identify XHTML 1.1 with public ID `-//W3C//DTD XHTML 1.1//EN` and system ID `http://www.w3.org/TR/xhtml11/DTD/xhtml11.dtd` (the HTTPS spelling is also accepted). No DTD is fetched. Internal subsets, entity declarations, `xml:base`, unsupported encodings, and unknown named entities are rejected. Without a DTD, only XML's five predefined named entities and numeric references are accepted. With the recognized XHTML 1.1 declaration, the one additional offline alias is `nbsp` → U+00A0. This is a limited entity subset, not a general XHTML entity resolver.

Source text uses decoded character values, not literal `&amp;`/`&#...;` spellings. XML line-ending handling is applied to linguistic text. CDATA inside a segment becomes ordinary text; its entity-like spellings are literal characters. Entity handling must respect XML lexical contexts, not globally replace strings inside comments or CDATA. Original byte positions must still refer to the unnormalized buffer: preprocessing `&nbsp;`, resolving references, CRLF normalization, and multibyte characters must never shift stored coordinates. A future XHTML reader needs lexical spans or a reversible position map; normalized parser text alone is insufficient. Existing structural OPF/NCX parsing must not be relaxed to implement this XHTML-specific policy.

Each original U+00A0, U+2007, or U+202F occurrence in editable flow, unless already inside an opaque subtree, is a protected atom (`nbsp` for U+00A0, `space` otherwise), regardless of whether written literally or as an entity. This preserves nonbreaking-space identity and its original spelling. Other ordinary spaces, tabs, and newlines inside a segment are editable linguistic text. `br` is a protected atom, not a segment boundary. Whitespace outside edited intervals stays byte-identical. Empty nodes are preserved, not turned into fabricated text.

None of these three scalars may occur in a `text` part of generated `source.json`, a response, or the validated parts passed to reconstruction. Check decoded JSON strings: literal UTF-8 and `\u00a0`/`\u2007`/`\u202f` escapes are equivalent. A response cannot introduce a new occurrence, replace an original atom with a literal scalar, or invent a new atom ID. Do not silently turn it into an ordinary space or repair its representation. Ordinary spaces, tabs, and newlines retain the existing XML rules. Immutable attributes, opaque spans, and other control strings remain original data, outside this `text`-part restriction.

Target character data escapes `&`, `<`, and `>`; U+000D is emitted as `&#13;` to avoid literal CR normalization. Other permitted characters are UTF-8. XML tags are never parsed out of target strings. JSON escaping is a separate step; JSON `"\u00e9"` and literal `"é"` denote the same character. XML rules are grounded in [XML 1.0 character data, references, and line endings](https://www.w3.org/TR/xml/); JSON syntax and string interoperability follow [RFC 8259](https://www.rfc-editor.org/rfc/rfc8259). The historical declaration is described by [XHTML 1.1](https://www.w3.org/TR/xhtml11/).

## Reconstruction requirements

The builder requires the operator-selected original EPUB, matching regenerated control, and a complete validated response set. It:

1. Reuse M0 ZIP/package/navigation validation, then regenerate the X mapping and compare control. Digesting, mapping, and copying refer to the same source byte snapshot; a changed source invalidates the operation.
2. For each target segment, first validate global atom order, ID-anchor placement, and the ban on protected-space scalars in decoded `text`, together with all other invariants. Then create only its replacement bytes: escaped target text plus the original paired start/end tokens and complete atomic source spans, in validated target order. Never use tags or attributes supplied by the response or automatically repair a rejected response.
3. Combine disjoint replacements against the original document coordinates, either by copying source slices in ascending order or applying changes in descending order. Never reuse old offsets against an already length-modified document.
4. Parse the result under the same offline XML policy and verify its protected topology, attributes, global atom order, document IDs, ID-anchor relative placement, and NCX boundary targets. Inline positions may move inside the authorized region only within these constraints; protected ancestors and references may not change. Full semantic validation of source hyperlinks, CSS, and translated meaning is not claimed.
5. Keep all bytes outside replacement intervals unchanged. Keep other uncompressed resources, OPF, NCX, CSS, and images unchanged; only body text regions are authorized for replacement. Write a new EPUB and publish it only after all checks succeed, retaining the original on every failure.

Three guarantees are distinct:

- **Resource and logical structure preservation:** original resource identities, paths, attributes, references, block structure, protected inline ancestry, global atom order, and ID-anchor relative placement survive. Authorized inline sibling movement within these constraints is intentional.
- **Unedited XHTML bytes:** bytes outside replacement intervals are identical. Original inline token/atom bytes are copied even if their positions inside an edited interval change. Text escaping, CDATA spelling, indentation, and entity spelling inside edited regions need not otherwise remain identical.
- **ZIP binary equality:** not promised. Compression, entry headers, or ZIP packaging can change. The rebuilt EPUB has a different whole-file digest.

This is viable without a whole-document serializer because every replacement covers one complete flow group and every protected lexical token has an original span. M1.1 must verify span fidelity with real examples before implementing dependent reconstruction. If a supported construct cannot be mapped without ambiguity, extraction must fail rather than provide a map that cannot be replayed.

## Contract cases

These are acceptance vectors represented across the extraction and parser/validator tests. JSON fragments below are case inputs, not additional file formats. Each case has an independent synthetic extraction unless it explicitly uses the complete mapping example. `source`/`target` in a vector are explanatory labels; response records still have only `id` and `parts`.

### X01 — Simple paragraph

Input XHTML: `<p>Hello.</p>`.

```json
{"source": [{"text": "Hello."}], "target": [{"text": "Olá."}]}
```

Expected: accept. Protects the enclosing paragraph and segment identity. Acceptance requires the expected segment ID exactly once, eligible Unicode text, and no added structural fields.

### X02 — Continuous inline text

Input XHTML: `<p>I said <i>this</i>.</p>`.

```json
{"source": [{"text": "I said "}, {"open": "i1"}, {"text": "this"}, {"close": "i1"}, {"text": "."}], "target": [{"text": "Eu disse "}, {"open": "i1"}, {"text": "isto"}, {"close": "i1"}, {"text": "."}]}
```

Expected: accept as one segment, not three text-node tasks. Protects the original `i` token pair. Accept only if `i1` opens/closes once with its original parent.

### X03 — Linguistic reordering

Input XHTML: `<p><i>Only then</i> did I understand.</p>`.

```json
{"source": [{"open": "i1"}, {"text": "Only then"}, {"close": "i1"}, {"text": " did I understand."}], "target": [{"text": "Eu entendi "}, {"open": "i1"}, {"text": "só então"}, {"close": "i1"}, {"text": "."}]}
```

Expected: accept the repositioned formatted span. Protects marker identity while allowing target word order. Accept when parent/stack rules hold; semantic correspondence of the emphasized words still requires linguistic review.

### X04 — Nested inline elements

Input XHTML: `<p><b>Very <i>small</i></b> room.</p>`; `i2.parent = b1`.

```json
{"source": [{"open": "b1"}, {"text": "Very "}, {"open": "i2"}, {"text": "small"}, {"close": "i2"}, {"close": "b1"}, {"text": " room."}], "target": [{"text": "Quarto "}, {"open": "b1"}, {"text": "muito "}, {"open": "i2"}, {"text": "pequeno"}, {"close": "i2"}, {"close": "b1"}, {"text": "."}]}
```

Expected: accept. Protects nesting, including parent identity. Acceptance requires balanced tokens and `i2` still inside `b1`; merely balanced tokens are insufficient.

### X05 — Internal link

Input XHTML: `<p>Read <a href="#note1" class="note">the note</a>.</p>`.

```json
{"target": [{"text": "Leia "}, {"open": "a1"}, {"text": "a nota"}, {"close": "a1"}, {"text": "."}]}
```

Expected: accept; replay must produce `<a href="#note1" class="note">a nota</a>`. Protects destination and attributes by copying the original tags. Any response attempt to set `href`, `class`, or token bytes is rejected as an extra field. Linked superscript callouts instead use one atom.

### X06 — Sections sharing XHTML

Input: the synthetic XHTML from the mapping example, with NCX destinations `Body.xhtml#start` and `Body.xhtml#next`; both use `d1`. This case has its own origin identity. The earlier complete example separately demonstrates the no-fragment case with the same physical intervals.

Expected: accept `q1 = [83,120)` with `s1`, and `q2 = [120,155)` with `s2,s3`. Protects document/section distinction and section coverage. Acceptance requires the same physical document, both navigation associations, and no dropped/duplicated segments. Two entries targeting the same normalized boundary would share a section, with both positions retained; a hierarchy is still retained in the navigation vector.

### X07 — Unindexed content

Input XHTML body: `<p>Prelude.</p><h2 id="c1">Chapter</h2><p>Text.</p>`; only NCX target is `#c1`.

Expected: accept a prefix section with `navigation_positions: []` containing the prelude segment, plus the indexed section. A document with no NCX entries similarly gets an unindexed section. Protects completeness. Dropping the prefix, `linear="no"` content, or a manifest XHTML without a spine entry fails coverage.

### X08 — Entities and Unicode

Input flow under the recognized XHTML 1.1 DOCTYPE: `<p>Caf&#233;&nbsp;☕ &amp; tea.</p>`.

```json
{"source": [{"text": "Café"}, {"atom": "nbsp1"}, {"text": "☕ & tea."}], "target": [{"text": "Café"}, {"atom": "nbsp1"}, {"text": "☕ e chá."}]}
```

Expected: accept; replay contains `Café&nbsp;☕ e chá.`. Protects decoded Unicode and the original nonbreaking-space atom. Accept only if `nbsp1` is retained once and strings contain valid XML characters, without Unicode/space normalization. The source spelling `&#233;` need not survive inside the edited region.

### X09 — Missing segment

Input: the complete example's response with `s3` absent, or only a response for section `q1` supplied as a complete translation.

Expected: reject as incomplete, identifying missing IDs and their document/section. Protects exact coverage. It may be accepted only as a batch when the separately selected batch set is exactly its IDs, never as final completion.

### X10 — Duplicate segment

Input: replace the complete response's `s2` record with both records below, keeping `s1` and `s3` unchanged:

```json
[{"id": "s2", "parts": [{"text": "Um."}]}, {"id": "s2", "parts": [{"text": "Dois."}]}]
```

Expected: reject duplication before applying either record, including duplication across files. Protects unambiguous identity. Equal texts do not make duplicates acceptable.

### X11 — Unknown identifier

Input: append `{"id":"s999","parts":[{"text":"Extra."}]}` to the complete example's response, whose expected segment IDs are only `s1,s2,s3`.

Expected: reject `s999`, even if other IDs are present. Protects the authoritative segment set. Unknown IDs are not appended or matched by text/title.

### X12 — Required marker removed

Input for complete example `s1`:

```json
{"id": "s1", "parts": [{"text": "Eu disse isto."}]}
```

Expected: reject missing `i1`, despite otherwise valid prose. Protects inline identity. Acceptance requires exactly the expected open/close pair.

### X13 — Duplicate or invalid nesting

Input variants for the X04 marker tree:

```json
{
  "duplicate": [{"open": "b1"}, {"open": "i2"}, {"text": "x"}, {"close": "i2"}, {"open": "i2"}, {"text": "y"}, {"close": "i2"}, {"close": "b1"}],
  "crossed": [{"open": "b1"}, {"open": "i2"}, {"text": "x"}, {"close": "b1"}, {"close": "i2"}],
  "reparented": [{"open": "b1"}, {"text": "x"}, {"close": "b1"}, {"open": "i2"}, {"text": "y"}, {"close": "i2"}]
}
```

Expected: reject all three, respectively for multiplicity, stack mismatch, and changed parent. Protects topology. Swapping two atomic siblings, such as `br1` and `img2`, also fails their fixed relative order.

### X14 — Wrong EPUB

Input: a translation carrying a different `extraction_id`, or an operator-supplied EPUB whose whole-file digest differs from control, even if its filename matches.

Expected: reject before applying text. Protects origin association. Acceptance requires the selected original digest and regenerated extraction identity, not a hash or path suggested by the translator.

### X15 — Altered reconstruction metadata

Input: complete example control modified to make `s1.range = [97,120)`, `i1.open = [104,108)`, or a document path different from the regenerated plan.

Expected: reject control mismatch even when the origin digest field is unchanged. Protects the source map. A response containing `range`, `parent`, or `attributes` is also rejected by the response schema. Checking only the EPUB hash is insufficient.

### X16 — Incompatible target structure

Input variants:

```json
{
  "unauthorized_part": {"id": "s2", "parts": [{"html": "<script>run()</script>"}]},
  "invalid_xml_character": {"id": "s2", "parts": [{"text": "\u0000"}]},
  "blank_text": {"id": "s2", "parts": [{"text": "   "}]},
  "empty_emphasis": {"id": "s1", "parts": [{"text": "Eu disse isto."}, {"open": "i1"}, {"close": "i1"}]}
}
```

Expected: reject unknown part shape, prohibited XML character, whole-segment blanking, and an emptied paired subtree, respectively. Protects safe character-data insertion and retained content inside formatting. Conversely, `<script>` inside a permitted `text` string is escaped and is not executable markup. Malformed JSON, duplicate object keys, and unknown fields are rejected independently of these structural cases.

### X17 — Atomic order across different parents

Input XHTML: `<p><i>One<br/>two</i><img src="image.png"/> End.</p>`. Markers `i1` and `img3` have parent `null`; `br2.parent = i1`. There are no ID-bearing elements or NCX boundaries in this segment.

```json
{
  "source": [{"open": "i1"}, {"text": "One"}, {"atom": "br2"}, {"text": "two"}, {"close": "i1"}, {"atom": "img3"}, {"text": " End."}],
  "target": [{"atom": "img3"}, {"open": "i1"}, {"text": "Um"}, {"atom": "br2"}, {"text": "dois"}, {"close": "i1"}, {"text": " Fim."}]
}
```

Expected: reject. Source atom sequence is `[br2, img3]`; target sequence is `[img3, br2]`. Multiplicity, stack balance, original parents, and each parent's atomic sibling order all remain valid. Only the global atomic sequence detects this inversion caused by moving `i1` across `img3`. Paired-group movement is allowed only when it preserves that sequence and the other invariants.

### X18 — XHTML anchor placement and empty anchors

First input XHTML: `<p><span id="note1">Important note</span> and <b>additional information</b>.</p>`. Both `span1` and `b2` have parent `null`. The original `span1` carries `id="note1"`; it is an anchor regardless of whether any link uses it. This example has no NCX reference to that ID.

```json
{
  "source": [{"open": "span1"}, {"text": "Important note"}, {"close": "span1"}, {"text": " and "}, {"open": "b2"}, {"text": "additional information"}, {"close": "b2"}, {"text": "."}],
  "accepted": [{"text": "Aqui, "}, {"open": "span1"}, {"text": "nota importante"}, {"close": "span1"}, {"text": " e "}, {"open": "b2"}, {"text": "informação adicional"}, {"close": "b2"}, {"text": "."}],
  "rejected_crossing": [{"open": "b2"}, {"text": "Informação adicional"}, {"close": "b2"}, {"text": " e "}, {"open": "span1"}, {"text": "nota importante"}, {"close": "span1"}, {"text": "."}]
}
```

Expected: accept the changed text with unchanged structural events and reject the sibling crossing. Both responses preserve multiplicity, parents, nonblank paired content, and the empty atom sequence. In the rejected response, the event set before `open(span1)` gains `open(b2)` and `close(b2)`. Moving either group across the other has the same forbidden effect. In the accepted response, leading text is permitted because this is not a promoted NCX boundary; such a boundary must also satisfy its existing text-position rule.

Second, independent input XHTML: `<p>Introduction <a id="chapter"></a> continues here.</p>`. The empty anchor is atom `a1`, parent `null`, whose complete original bytes are `<a id="chapter"></a>`. This ID also has no NCX association in the example.

```json
{
  "source": [{"text": "Introduction "}, {"atom": "a1"}, {"text": " continues here."}],
  "accepted": [{"text": "Introdução "}, {"atom": "a1"}, {"text": " continua aqui."}],
  "rejected_missing": [{"text": "Introdução continua aqui."}],
  "rejected_duplicate": [{"text": "Introdução "}, {"atom": "a1"}, {"atom": "a1"}, {"text": " continua aqui."}]
}
```

Expected: accept only the response retaining `a1` exactly once. Its marker identity, raw bytes, ancestry, global atom order, and anchor placement are preserved; no editable text is invented inside it. Removal or duplication is rejected despite otherwise valid prose. An anchor outside a segment instead remains in the preserved original intervals. Neither representation proves that translated words have retained their original semantic relationship to the anchor.

### X19 — Protected whitespace introduced in text

Input flow under the recognized XHTML 1.1 DOCTYPE: `<p>Hello&nbsp;world.</p>`. The original nonbreaking space is atom `nbsp1`, parent `null`. The three introduced-space variants below deliberately retain this original atom, isolating the prohibited addition in `text` from marker multiplicity or ordering failures.

```json
{
  "source": [{"text": "Hello"}, {"atom": "nbsp1"}, {"text": "world."}],
  "accepted": [{"text": "Olá"}, {"atom": "nbsp1"}, {"text": "mundo."}],
  "rejected_added_nbsp": [{"text": "Olá"}, {"atom": "nbsp1"}, {"text": "mundo\u00a0hoje."}],
  "rejected_added_figure_space": [{"text": "Olá"}, {"atom": "nbsp1"}, {"text": "mundo\u2007hoje."}],
  "rejected_added_narrow_nbsp": [{"text": "Olá"}, {"atom": "nbsp1"}, {"text": "mundo\u202fhoje."}],
  "rejected_replaced_atom": [{"text": "Olá\u00a0mundo."}]
}
```

Expected: accept only the response with the existing atom and ordinary editable text. Reject each introduced scalar after decoding JSON, whether expressed by an escape or literal UTF-8. The replacement variant violates both required-atom multiplicity and the ban on protected scalars in `text`. These are structural rejections even if the translation is linguistically correct; do not normalize the character, synthesize an atom, or repair the response. Generated source parts must obey the same prohibition, converting eligible original occurrences into atoms during extraction.

## Reference-book feasibility study

The locally available **Baka to Test to Shoukanjuu — Volume 01** was examined read-only during specification. Its three spine XHTML documents include illustration-only cover/illustration bodies; `Body.xhtml` contains the narrative, all 12 NCX destinations, and notes. The first destination has no fragment; the other destinations resolve to `h1` IDs. This fits disjoint sections within one document without chapter-per-file assumptions.

Observed structures include paired `i`/`b`/`strong`, `span`, `big`, `font`, `sub`, `br`, linked superscript callouts, list-item note IDs, nested tables with both `td` and `th`, and complete SVG illustration subtrees. XHTML 1.1 DOCTYPE declarations and one `&nbsp;` occurrence motivate the explicit offline entity policy. Direct cell/container text motivates flow groups rather than a `p`-only extractor. Numerous `title` attributes remain a documented translation limitation; external links must be preserved without fetching their destinations.

This is structural evidence for the proposal, not an extraction/rebuild test or a claim that M1.1 already supports the book. No book content, original archive, or generated book fixture is added to the repository; all examples above are synthetic.

## Limitations and deferred work

- Extraction supports the specified EPUB 2/XHTML vocabulary, UTF-8, and offline entity subset. EPUB 3, arbitrary DTDs/entities, `pre`/inherited `xml:space="preserve"`, MathML, ruby, form content, and other unknown constructs need explicit support. Unsupported constructs fail extraction rather than yielding a complete-looking partial result.
- Fragment targets requiring a mid-segment split are rejected. Chapter boundaries are not inferred from typography, filenames, or headings absent from NCX.
- All attributes, head text, OPF metadata, NCX labels, `pageList`, and `navList` remain untranslated. SVG/image text and textual attributes such as `alt`/`title` require an explicit extension, not silent translation under 1.0.
- Extraction prioritizes preservation of original protected spaces over introducing new nonbreaking spaces required by a target language. U+00A0/U+2007/U+202F are forbidden in `text`; only existing atoms can represent them.
- Internal/external hyperlink values are preserved; complete link-semantic auditing, computed CSS visibility/generated content, CSS whitespace/layout, and visual equivalence are not guaranteed. Translation can change line wrapping and pagination. Existing executable source content is preserved, not sanitized; target prose never becomes markup.
- No structural validator can establish translation quality, detect an intentionally mislabeled but structurally compatible sentence, prove that emphasis still surrounds the semantically corresponding words, or guarantee an anchor's exact semantic position. Anchor identity, ancestry, and placement relative to protected structural events are checked; linguistic equivalence and complete link/reference semantics are not. Linguistic review remains external.
- Parser APIs, lexical-mapping mechanics, and resource budgets are implementation details described in the architecture documentation. JSON Schema tooling, target-language metadata, and commands beyond extraction remain deferred. Such changes must not alter these identity/authority rules without versioning. Model orchestration and a configuration system remain outside extraction scope.
